Carrom-Playing Robot: Perception and Strategy

A research project to build a robot that physically plays carrom against human opponents. I built the software that lets it see the board and decide its shot.

1. Objective

The aim is a robot that plays real carrom, on a real board, against a human. This is harder than playing carrom in a simulator: the robot has to see the physical coins through a camera, decide what to hit and how, and then execute the shot with a mechanism.

The project is carried out at the Indian Institute of Information Technology, Design and Manufacturing (IIITDM), Kancheepuram, under Dr. Nagamanikandan G.

4. Part 1: Perception stack

A single overhead webcam looks down at the board. The stack turns that image into a list of coins and the striker, each with its exact position in millimetres in a fixed board frame. It combines a trained YOLO detector with classical OpenCV image processing.

How it works

  1. Find the board. Four ArUco markers at the board's corners are detected, so the board is located reliably even if the camera shifts slightly.
  2. Rectify the view. A homography maps the four marker centres to a perfect square, turning the tilted camera view into a flat, top-down 1000 × 1000 image where one pixel is about 0.74 mm.
  3. Detect with YOLO. A YOLO11s model, fine-tuned on carrom images, finds every black coin, white coin, the red queen and the striker, giving a bounding box and class for each.
  4. Refine each detection. A bounding box is only approximate, so inside each box a Hough circle transform fits the coin's actual circle, giving a precise centre and radius.
  5. Validate by physical size. A fitted circle whose radius does not match a real coin or striker (12.5–18 mm and 20–21.5 mm) is rejected as a false positive.
  6. Report positions. Centres are converted to millimetres in a board-centred frame (origin at the board centre) and saved as JSON, along with an annotated image.

An optional enhancement step (contrast and sharpening) helps in poor lighting, and a single command runs the whole pipeline from camera photos to JSON results. All parameters live in one configuration file.

Results: how repeatable is it?

To test stability, an unmoved board with five coins was captured 41 times and the pipeline run on every image. The detected position of each coin barely changed between captures.

All thresholds and parameters are kept in one configuration file, so the pipeline can be retuned for different lighting or hardware without touching the code.

5. Part 2: Strategy engine

Given the board, the engine returns one answer: where to place the striker, in which direction to hit, and with what speed. It is rule-based, built on geometry and physics, and is a pure function with no dependency on any simulator, so the same code can drive a game, a physics simulation or the real robot.

How it decides a shot

  • Ghost-ball geometry. It computes the exact point where the striker must be at the moment of contact to send a coin toward a pocket.
  • Chains built backwards. A plan starts at the pocket and works back to the striker, covering direct shots and two-coin combinations.
  • Wall bank shots. Bounce points are solved with the real reflection law, accounting for the wall's energy loss.
  • Exact striker placement. Shadow-casting finds every spot on the baseline with a clear line to the aim point, and the gentlest cut angle is chosen.
  • Ranking. Candidates are scored on collisions, bounces, hit angle and distance.
  • Speed solving. Friction, collision momentum and wall losses are worked backwards through the plan to find the launch speed that just carries the coin into the pocket.

A game to test it

To judge how well the algorithm plays, I built a desktop game with a real-time physics simulation and an ICF-style rules referee. A human can play against the engine digitally and see how it performs. Run it with a single command:

pip install -r requirements.txt
python3 run_game.py

6. What is next: reinforcement learning

The rule-based engine is the foundation. I am now working on a reinforcement-learning approach, with training planned in a physics simulator such as MuJoCo or Isaac Lab, so the robot can learn strategies beyond hand-written geometry. This work is in progress.
